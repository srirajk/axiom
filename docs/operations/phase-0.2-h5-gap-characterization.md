## Later G-07 Axiom-only source increment (2026-10-02; not deployed)

`AgentExchangeAuthorityService.resolveWorkforce` now requires the human token's registered public client and the requesting workload's confidential client to have the same tenant-application UUID before looking up workforce authority. `AgentExchangeAuthorityServiceTest` retains the same-application positive path and adds a cross-application denial with OAuth `invalid_grant`; its targeted suite passed **11/11**. The post-change Java 25 server suite passed **358 tests, 0 errors, 0 failures, 0 skipped**. This closes the implicit cross-application authority borrowing path in source, but no isolated deployed endpoint or original rollout was tested. Explicit cross-application delegation, if ever required, needs its own approved authority contract; this check does not create one. Recovery is to revert the one application-ID equality check and its negative test in this clone, then rerun targeted/full tests. The installed H-5/G-07 observation below remains a record of the pre-fix release.

## Later G-13 Axiom-only admin-disable increment (2026-10-02; not deployed)

`UserService.updateUser` now calls `IamSessionService.revokeAllForPrincipal` whenever an admin sets `isActive=false`; `deleteUser` does the same for soft deletion. `ScimService.replace` and `patchUser` also revoke sessions when they leave a user inactive. Each principal change and session revocation participates in the same service transaction. Non-deactivating admin/SCIM updates do not revoke sessions. `IamSessionService.active` additionally rejects an otherwise active session when its matching principal row is disabled or belongs to another tenant. This closes the validation side of a session inserted after a disable transaction's revocation scan; a focused unit test exercises that ordering's resulting state. The post-change Java 25 server suite passed **364 tests, 0 errors, 0 failures, 0 skipped**. This adds a principal lookup to session validation and must be included in Phase 0.5 latency/freshness review. An actual two-transaction disable/login race and isolated deployed endpoint check remain; G-13 is therefore still open. Recovery is to revert the bounded `UserService`, `ScimService`, and `IamSessionService` changes in this clone, then rerun focused/full tests; no schema or deployed release was changed.

## Later G-02 Axiom-only source increment (2026-10-02; not deployed)

The next source step serializes both registration paths on the same `tenant_application_clients` row via a pessimistic write lock before checking the broker or workload table. That client ID has a unique constraint in Flyway V15. Both services are transactional, so the lock is held through their registration transaction. Focused tests verify lock-before-cross-table-check ordering and passed **12/12** under Java 25. The post-lock full server suite passed **355 tests, 0 errors, 0 failures, 0 skipped**. This is a source-level race mitigation, not yet a two-transaction PostgreSQL concurrency proof or installed-release evidence. Reverting the new repository lock method and the two service calls restores the prior behavior in this clone; no schema migration or deployment was made.

`BrokerWorkloadRegistrationLockIT` then used a disposable local PostgreSQL 16 container with the real Flyway V1–V29 schema. Two independent transactions contested the same client row in each order: broker-first/workload-second and workload-first/broker-second. In both, the second transaction waited for the first commit, observed the opposing row, and did not insert; **2/2 Failsafe tests passed**, with no errors or skips. The container and its database were removed automatically; no Kubernetes resource was touched. This proves the PostgreSQL lock/lookup pattern, while the unit tests prove both service paths call the lock before their conflicting lookup. It is not yet an end-to-end concurrent service request or isolated deployed-release test, so G-02 remains open there.

The broker-first ordering gap has a narrow source correction in this clone: `CiamDelegationService.registerWorkload` now checks the tenant's broker repository before saving a workload, matching the pre-existing reverse check in `AgentExchangeAuthorityService.registerBroker`. `CiamDelegationServiceBrokerExclusivityTest` proves a broker-registered-first client is denied without saving a workload and an independent confidential client still registers. A subsequent test explicitly verifies that a workload-registered-first client cannot become a broker. The two focused suites passed **12/12** after that test addition. The full Java 25 server suite passed immediately after the production-code change and before the reverse-case test was added; Surefire then reported **354 tests, 0 errors, 0 failures, 0 skipped**. Testcontainers were absent after that run. There was no migration or deployment. This proves sequential registration behavior in source; concurrent cross-table registration and the installed test release remain unverified. Recovery is to revert the repository check and constructor injection in the clone, then rerun focused and full tests. The historical H-5 observation below remains the pre-fix installed behavior.
