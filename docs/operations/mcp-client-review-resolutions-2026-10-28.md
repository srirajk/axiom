| B4 | Internal IDs are generated once and persisted; they do not depend on an in-memory cache. A fresh Axiom application against the same test database/Redis/signing keys refreshes an earlier token during a simulated vendor outage. Editing or reapproval creates a new approval generation; deletion/narrowing withdraws old sessions and authorizations. The proposed globally unique external URL is intentionally rejected: each tenant/application can approve the same vendor independently. A deterministic URL hash is unnecessary when IDs are persisted and would need an approval generation to avoid reviving withdrawn grants. |

One review statement also needs correction: Spring 1.5.8's refresh provider checks DPoP binding **if a proof is present**; it does not require DPoP for all public refreshes. Axiom uses rotation/replay withdrawal for public refresh security. See the [Spring 1.5.8 provider](https://github.com/spring-projects/spring-authorization-server/blob/1.5.8/oauth2-authorization-server/src/main/java/org/springframework/security/oauth2/server/authorization/authentication/OAuth2RefreshTokenAuthenticationProvider.java).

Assertion authentication follows [RFC 7523](https://datatracker.ietf.org/doc/html/rfc7523). Resource binding follows [RFC 8707](https://datatracker.ietf.org/doc/html/rfc8707). Local-callback consent and host display address the [MCP localhost impersonation considerations](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization#localhost-redirect-uri-risks). A public native client ID cannot cryptographically prove which local process owns a callback; explicit user approval and the warning remain necessary.
