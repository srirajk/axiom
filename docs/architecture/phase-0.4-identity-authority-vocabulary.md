# Phase 0.4 — identity and authority vocabulary (Axiom-side draft)

Status: **Axiom-side increment tested; joint Argus mapping parked at the owner's request on 2026-10-02**. This is a source-traced Axiom contract, not yet a jointly verified Argus provisioning, policy-input or audit contract. The Axiom clone has narrow validation and audit-detail changes described below, but no deployment or token-format change. Do not mark the joint 0.4 story Done.

## Objects and ownership

| Term | Stable identifier and owner | Meaning / boundary |
|---|---|---|
| Tenant | `tenant_id`, Axiom | Issuer-side security partition. A dedicated instance does not make this claim interchangeable with an Argus Use Case or application. |
| Application | Axiom application UUID | Product/client registration and access boundary, not a logical Agent or a run. |
| OAuth client | `client_id`, Axiom | Credentialed OAuth party (public browser or confidential service); may represent a BFF, broker or workload. It is **not** by itself the business actor, Agent, or deployment. `TenantApplicationClient.id` is a different database UUID. |
| Workload identity | `AgentWorkloadIdentity.id` UUID and `workload_ref`, Axiom | Registered acting service identity bound to one OAuth client. `act.workload_id` and `act.sub` identify this workload on exchanged tokens; `act.client_id` names its client. Its deployment may change without changing the logical product Agent. |
| Trusted exchange broker | `TrustedExchangeBroker.id` UUID, Axiom | Gateway exchange authority bound to its own OAuth client and gateway audience. The broker performs exchange but does not become the business actor in `act`. |
| Exchange route | `AgentExchangeRoute.id` UUID, Axiom | Bounded source-workload → audience/destination authority with scopes, purpose, expiry and status. For route-backed tokens this UUID is `authority_id`. It is neither the token ID nor a run/branch ID. |
| Workforce entitlement | `application_id` + user subject + revision, Axiom | Application membership/role decision for a human. A workforce exchange currently encodes this as `authority_id=workforce:<app UUID>:<subject>:<revision>`; this is **not** a route UUID. |
| Customer grant | `CustomerDelegationGrant.id` UUID, Axiom | Customer consent/delegation to one workload, audience and scopes. Customer `delegation_id` and `authority_id` refer to the grant, not an Argus chain graph. |
| IAM token session | `IamSession.id` UUID, Axiom | Durable per-OAuth-authorization token-session index used by access-token `sid` and revocation checks. Exchanged tokens carry `subject_sid` for the original human session and a new `sid` for their own authorization. OIDC ID-token `sid` has a separate framework logout meaning. |
| Logical Agent | New Argus Authoring `first_party_agents.id` UUID; legacy Gateway `AgentManifest.agent_id` is a separate string | Product-level Agent definition. The Authoring UUID is carried as composition `agent_ref`, whereas composition `agents[].id` is local to a Use Case draft. A registry `agent_id`, OAuth `client_id`, Axiom workload UUID and pod name must not be assumed equal. |
| Agent deployment | Current Argus Authoring `agent_deployments.agent_id` (one row per first-party Agent) plus revision, identity mode/subject and connection reference | Deployment configuration for the logical Agent. The current table does **not** have an independent deployment UUID or multiple rows per environment; do not invent one in an API or token. Axiom signing-key `deployment_id` is an unrelated **issuer key-management field**. |
| Use Case assignment | Current Argus Authoring key `(draft_id, local_agent_id)` plus `agent_id`, revision/status and assignment hash | An Agent's membership/configuration in a Use Case draft; the current table has no standalone assignment UUID. Do not duplicate this relationship inside Axiom's application-role assignments or exchange-route table. Approved, released runtime authority still requires separate verification. |
| Run, context, branch | Argus-owned IDs (**not yet verified**) | Runtime execution and trace/control context. They do not currently appear in Axiom-issued access-token claims. If a later phase needs an opaque context reference, its ownership, binding and freshness must be agreed before issuance. |
| Access token | JWT `jti` if present; `sid` session ID; `aud` recipient | Short-lived proof of the particular issued authorization. A token is not a persistent delegation chain, run, branch or configuration record. |

## Current claim contract, not a proposed full lineage graph

`sub` is the human/customer or autonomous workload **subject** and remains that subject through an exchange. `identity_kind` says workforce, customer or workload. `client_id`/`azp` name the redeeming OAuth client on exchanged tokens. `act` names the acting workload; the trusted broker can redeem without replacing `act`. `aud`, `scope`, `purpose`, `authority_profile`, `token_use` and `authority_id` express the single hop's authority. `sid` identifies this token's Axiom session and `subject_sid` links to the root human session for checks. A route-backed hop uses the route UUID for `authority_id`; workforce and customer profiles have different authority-ID formats as above. None of these claims silently stands for an Argus Agent definition, assignment, deployment, run, context or branch.

The preferred later cross-product contract is an explicit mapping held in provisioning records and audit evidence: Argus first-party Agent UUID → its deployment revision and verified identity subject → Axiom workload UUID/client ID, with the Argus Use Case draft/assignment key and run/branch IDs remaining Argus-owned. Axiom may validate an agreed opaque reference at an exchange/enforcement point, but should not embed a transitive delegation tree or mutable run state in JWTs. This is a proposal, **not existing implementation**. The legacy Gateway manifest's string `agent_id` needs an explicit alias/migration rule, not an implicit equality assumption.

## Policy and audit meaning

Axiom policy/authority checks should receive tenant, subject/identity kind, acting workload UUID/client, recipient audience, requested scopes, authority profile/ID and current authority status. Argus should add its own Use Case assignment, logical Agent, deployment, run, branch and resource/action context at its enforcement points. Axiom's `CiamLifecycleAuditService` currently records tenant, actor, event type, subject type/ID, details and correlation ID; the broker and route registration/revocation paths record their persisted IDs. A joint audit envelope tying these to Argus run/branch identifiers is **not implemented or verified**. IDs and outcomes may be logged, not bearer tokens or reusable secrets.

### Verified Authoring-to-runtime gap

The current Argus `ReleaseAccess.assign` resolves a capability's `agent_refs` against composition-local `agents[].id`, not the stable `agents[].agent_ref` UUID. For an assigned Agent it emits a policy expression based on verified subject and actor strings, then `records(useCase)` emits `binding` and `agent` records keyed by those strings with allowed routes. Those runtime records do not carry the first-party Agent UUID, deployment revision, assignment revision, or assignment hash. `ReleaseCompiler` includes the local `agent_refs` in capability records, but the read-only trace does not establish that a receiver joins them to the first-party UUID at enforcement. The Argus security standard itself calls the current single `binding:{subject}` lookup insufficient for a shared identity in two Use Cases. This is a **contract gap**, not an assertion that the target model is deployed or secure. Axiom must not infer the Argus assignment from a matching client/subject string.

The Argus Decision image confirms the present enforcement shape. `ResolveContextStage` resolves exactly one active `BindingRecord` by verified token subject and takes its `useCaseRef`; it does **not** accept a caller-supplied Use Case. `PinRouteStage` then requires the route in that binding and, when `act.sub` is present, also requires an active `AgentRecord` keyed by workload subject that allows the route; an unknown actor denies. `GrantStage` checks an active `(use_case_ref, route_id)` grant and its time window. This is real layered route authorization, but `BindingRecord` and `AgentRecord` have no first-party Agent UUID or Use Case-assignment revision, and subject-keyed resolution is not enough for shared-Agent continuation across two Use Cases. The source trace is not a fresh installed-runtime test.

The current **dedicated quickstart fixtures** use matching actor-subject strings across both repositories. Read-only `jq`/`diff` checks returned exit 0 for Axiom-clone `agent-workloads.jsonl` `workloadRef` against Argus `onboarding.json` `records.agent[].workload_subject` for `agent:quickstart-entry:development` and `agent:quickstart-agent:development`; the same comparison passed for `agent:quickstart-bff:development` in Argus `human-bff/records.json`. This proves fixture spelling only. It does not prove those exact records are currently installed, or that Authoring's stable first-party Agent UUID/revision is joined to them.

Argus's `DecisionTraceLogger` logs trace ID, Use Case, route, subject, actor, verdict and stage record references. Its own documentation says that operational decision trace is **not** complete durable lineage; dispatch and destination-completion facts belong to other boundaries. On the allowed path, the current `PinRouteStage` returns a route `RecordRef`, while the Agent record checked for actor-route permission is not added to its `reads`; therefore that stage trace alone cannot identify the exact Agent-record version behind an allow. This is a read-only evidence-contract finding, not a change to Argus or a claim that the route check was skipped.

An Axiom regression now verifies a narrower safe boundary: `JwtClaimsCustomizerTokenExchangeTest` supplies `use_case_id`, `run_id`, `context_id` and `branch_id` on an input token, and checks that the exchanged token does **not** copy them as authority. The test still asserts the distinct subject, broker `client_id`, actor workload and route `authority_id`. Targeted Maven Surefire passed **2 tests, 0 failures, 0 errors, 0 skipped** on 2026-10-02. This does not supply the missing trusted Argus continuation profile or live assignment check.

A second Axiom regression in `AgentExchangeAuthorityServiceTest` uses a valid gateway token as a control, then independently substitutes the actor workload UUID, workload reference and OAuth client. All three substitutions must fail as OAuth `invalid_grant`. The first run exposed a real error-contract inconsistency: an unknown workload UUID escaped as `EntityNotFoundException` rather than OAuth denial. `AgentExchangeAuthorityService.requireActiveActor` now maps that lookup failure to `invalid_grant`; no authorization is newly allowed. After the correction, targeted Surefire passed **8/8** service tests and **2/2** claim tests, with no failures/errors/skips. This is source/test evidence only; the corrected server has **not** been built into or deployed to the isolated namespace, and no Argus or original Axiom installation changed. Recovery is a revert of this narrow error mapping and test addition if an unforeseen consumer requires the old exception, followed by the same targeted tests; no data migration is involved.

The complete server `mvn -q test` suite was then run with Java 25. An initial sandbox-only run reached 349 tests but had three environment errors because localhost binding and Docker were denied; it was not accepted. With local network/Docker permission granted, the rerun exited 0: Surefire reports **129 suites, 349 tests, 0 failures, 0 errors, 0 skipped**. No Testcontainers remained running under their Docker label after process exit. This validates local regression behavior, not deployed-image behavior.

The subsequent Axiom-only audit-contract increment makes exchange-route create and revoke events use one details shape: source workload UUID, destination type, optional destination workload UUID, audience, scopes and expiry. Previously create omitted the destination UUID and revoke logged only the audience, making the route lifecycle difficult to interpret without a later database join. A targeted test checks both events use workload IDs rather than Agent names; `AgentExchangeAuthorityServiceTest` passed **9/9** after this increment. No schema migration, token claim or authorization decision changed. These event details remain limited to Axiom lifecycle evidence; they do not claim an Argus first-party Agent UUID or run ID. The earlier 349-test run predates this audit-details increment, so it must not be cited as a post-change full-suite result. Recovery is to revert the details-shape helper and rerun the targeted test; the underlying route records are untouched. This code is not deployed.

After that increment, the full Java 25 server suite was rerun with local Docker/localhost access and exited 0: **129 suites, 350 tests, 0 failures, 0 errors, 0 skipped**. This supersedes the earlier 349-test result for the current source. The suite used disposable Testcontainers, not the original Axiom or Argus deployments.
